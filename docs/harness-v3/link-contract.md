# 링크 규약과 해석 계약

장부(설계 §6.2)와 그 주변 문서를 잇는 링크를 어떻게 쓰고 어떻게 해석하는지 정합니다. 설계 §6.6이 정본이고, 이 문서는 그것을 구현할 수 있는 규칙으로 풀어 씁니다. 해석기는 `scripts/links.py`, 계약 사례는 `references/link-contract.fixtures.json`입니다. 셋이 어긋나면 fixture가 맞습니다.

## 1. 어떻게 쓰나

| 방향 | 쓰는 법 | 예 |
|---|---|---|
| 문서 → 태스크 | `[[dag#<태스크 ID>]]`, AC는 `[[dag#<ID>/AC-n]]` | `[[dag#MIG.DEV-0045]]`, `[[dag#MIG.DEV-0045/AC-1]]` |
| 장부 → inbox | 장부 키 디렉토리 기준 경로 | `[[inbox/MIG.DEV-0045/plan]]` |
| 옮길 수 있는 문서(결정 기록, 논의) | 앞머리 `id`로 | `[[D-0001]]` (`decisions/D-0001.md`의 앞머리 `id: D-0001`) |
| 저장소 밖, 다른 장부 키 | **커밋 고정 주소** | `https://github.com/<owner>/<repo>/blob/<커밋>/<경로>#<앵커>` |

- 다른 장부 키로 가는 링크는 같은 장부 저장소 안이어도 커밋 고정 주소로 씁니다. 남의 장부는 계속 바뀌기 때문입니다(설계 §6.6, T-069 나-4).
- `dag.md`는 태스크마다 **ID만의 heading**(`### MIG.DEV-0045`)을 두고 제목은 그 아래 줄에 씁니다(show-dag-stack이 schema 3 장부에서 만듦). 제목이 바뀌어도 ID 링크는 그대로입니다.

## 2. 이름공간과 식별자

- **장부 저장소**: 장부들을 담은 저장소 하나(예: `zeno0505/note`). 해석은 이 저장소 루트 안에서만 합니다.
- **장부 키**: 한 에이전트의 장부 디렉토리 이름이자 `dag.yaml` 맨 위 `ledger_key`(예: `MIG.DEV`). 대문자와 점.
- **태스크 ID**: `<장부 키>-<번호>`(예: `MIG.DEV-0045`). 장부 안에서 하나.
- **AC**: `<태스크 ID>/AC-n`.
- **문서 ID**: 옮길 수 있는 문서의 앞머리 `id`(예: `D-0001`). 저장소 안에서 하나여야 합니다.
- **옛 ID**: v2 장부의 ID(예: `T-091`). v3 태스크의 `legacy_ref: "<옛 dag 경로>@<커밋>#<옛 ID>"`로만 이어집니다.

## 3. 해석 규칙

1. **`dag`는 장부 키 디렉토리의 `dag.yaml`**: 링크가 적힌 문서에서 위로 올라가며 처음 만나는 `dag.yaml`이 있는 디렉토리입니다. inbox가 몇 단계로 중첩돼도 같습니다(전제: inbox 안에는 `dag.yaml`을 두지 않습니다). `dag`, `dag.md`, `dag.yaml`은 모두 같은 장부를 가리킵니다(확장자 생략·변형 허용). 앵커 없는 `[[dag]]`는 장부 파일 자체(`target.file`)로 해석합니다.
2. **앵커는 태스크 ID**: heading 문구가 아닙니다. 앵커에 공백이 있으면(예: `MIG.DEV-0045 가입 코드`, 제목 붙은 heading의 앵커) ID 링크가 아니므로 `unsupported`입니다. 빈 앵커(`[[dag#]]`), 빈 AC(`ID/`), 태스크 없는 AC(`/AC-1`)도 `unsupported`입니다. 공백 없이 하이픈으로 이어진 heading 슬러그(`MIG.DEV-0045-가입-코드`)는 ID와 구별할 수 없어 그 ID가 없다고 보고 `missing`이 됩니다.
3. **태스크를 찾는 순서**: `dag.yaml` → `archive/index.yaml`(접혀서 보관된 태스크, 설계 §6.11) → `legacy_ref`(옛 ID). 앞에서 찾으면 뒤는 보지 않습니다. `legacy_ref`는 경로가 옛 `dag.yaml`(또는 `dag`, `dag.md`)일 때만 옛 ID로 봅니다 — 체크리스트 줄을 가리키는 `…/e2e-checklist.md@<커밋>#L2`의 `L2`는 태스크 ID가 아닙니다.
   - `ID/AC-n`: `dag.yaml`과 `legacy_ref`로 찾은 태스크는 AC가 실제로 있는지 봅니다(없으면 `missing`). 보관된 태스크는 보관 색인에 AC가 없어 확인할 수 없으므로 `target.ac`를 남기고 경고 `ac-unverified`를 붙입니다.
   - 보관 색인에는 `legacy_ref`가 없어, 이관된 뒤 접힌 태스크의 옛 ID 링크는 `missing`이 됩니다.
   - `dag.yaml`에 같은 ID가 둘 이상이면 `ambiguous`(중복 앵커).
   - 같은 옛 ID를 가리키는 태스크가 둘 이상이면(옛 장부가 달라도) `ambiguous`. 문자열만으로 합치지 않습니다.
4. **대소문자는 구별합니다.** `mig.dev-0045`는 `MIG.DEV-0045`가 아니라 `missing`이고, 결과에 비슷한 ID를 `hint`로 붙입니다. 경로도 대소문자까지 맞아야 합니다(`plan.MD` ≠ `plan.md`). `[[../mig.dev/dag#…]]`처럼 dag 링크의 디렉토리 이름도 마찬가지입니다. 대소문자를 무시하는 파일 시스템(macOS 기본)에서도 결과가 같도록 실제 파일 이름과 맞춰 봅니다. 한글 같은 이름은 유니코드 정규화(NFC)로 맞춘 뒤 비교합니다 — macOS가 NFD로 저장한 `계획.md`도 NFC로 쓴 링크로 찾습니다.
5. **퍼센트 인코딩은 풀어서** 해석합니다(`MIG%2EDEV-0045` = `MIG.DEV-0045`).
6. **경로 링크**(`/`가 있거나 `.`으로 시작)는 장부 키 디렉토리 기준입니다(장부 밖 문서면 그 문서의 디렉토리 기준). 확장자가 없으면 `.md`를 붙입니다. 이름에 점이 들어 있어도(`notes.v2`) 그 이름 그대로인 파일이 없으면 `.md`를 붙여 찾습니다. `|별칭`(표 안에서는 `\|`)과 `#앵커`는 파일을 찾는 데 쓰지 않고, 앵커는 `target.anchor`로 남깁니다. 저장소 루트 밖으로 나가면(`../`, 절대 경로, 안에 있지만 밖을 가리키는 심볼릭 링크) `out-of-scope`입니다.
7. **문서 ID 링크**(`/`가 없는 한 단어, `#앵커`는 붙을 수 있음)는 저장소 안 `.md` 문서의 앞머리 `id`로 찾습니다. 문서를 옮겨도 그대로 이어집니다. 같은 `id`가 둘이면 `ambiguous`. 저장소 밖을 가리키는 링크 파일은 읽지 않습니다.
8. **다른 장부 키**: 장부 안 문서에서 같은 저장소의 다른 장부 키 안을 가리키면(`[[../MIG.QA/dag#…]]`, 경로 링크, 문서 ID 링크 모두) 해석은 하되(`resolved`) 경고 `unpinned`를 붙입니다. 장부 밖 문서(예: 저장소 루트의 README)에서 가리키는 것은 "다른 장부"가 아니므로 경고하지 않습니다.
9. **커밋 고정 주소**: `https://github.com/<owner>/<repo>/blob/<ref>/<경로>?<질의>#<앵커>`를 저장소·커밋·경로·앵커로 나눕니다(질의 문자열은 버림). `<ref>`가 커밋(16진수 7~40자, 대소문자 무관)이면 `resolved`, 가지 이름이면 `resolved` + 경고 `unpinned`. 가지 이름에 `/`가 있으면(`feature/x`) 주소만으로 가지와 경로를 가를 수 없어 첫 마디를 가지로 봅니다 — 커밋 고정 주소를 쓰면 생기지 않는 문제입니다. `tree/` 주소와 그 밖의 주소, 스킴이 붙은 위키 링크(`notion://…`, `[[run:…]]`)는 `unsupported`입니다.

## 4. 결과

| 결과 | 뜻 |
|---|---|
| `resolved` | 대상을 하나 찾음. `target`에 장부 키·태스크·AC, 또는 파일, 또는 저장소·커밋·경로 |
| `resolved(archived)` | 장부에서 접혀 `archive/index.yaml`에 있음. `target`에 요약 위치와 inbox 경로 |
| `missing` | 형식은 맞지만 대상이 없음 |
| `ambiguous` | 대상이 둘 이상. `candidates`가 있으면 후보 |
| `out-of-scope` | 장부 저장소 밖 |
| `unsupported` | 모르는 형식 |

- **`denied`는 해석 결과가 아닙니다.** 리졸버는 읽기 권한을 보지 않습니다. 링크가 맞다고 읽기 권한이 생기지 않으며, 권한 검사와 거부(`denied`)는 읽는 쪽이 합니다.
- 경고(`warnings`)는 결과와 따로 붙습니다: `unpinned`(커밋 고정이 아님), `ac-unverified`(보관된 태스크의 AC라 있는지 확인 못 함).
- 리졸버는 형식이 깨진 `dag.yaml`·보관 색인에서도 예외 없이 결과 여섯 가지 중 하나를 냅니다(대개 `missing`).

## 5. 열람 도구(note-app 등)가 맞출 계약

열람 도구는 교체 가능한 구현입니다(설계 §2, §7.6). 하네스는 특정 열람 도구에 맞추지 않고, 열람 도구가 아래를 지킵니다.

- **fixture로 동작을 맞춥니다.** 다른 언어의 열람 도구는 `links.py`를 실행하지 않고 `link-contract.fixtures.json`의 모든 사례를 통과하도록 구현합니다. fixture 형식: `tree`(경로 → 내용)를 빈 디렉토리에 만들고(`tree_patch`가 있으면 그 사례만 덮어씀), 사례마다 `from` 문서에서 `link`를 해석한 결과를 `expect`와 비교합니다. 비교는 **부분 집합**입니다: `expect`에 적힌 키만 보고, 값이 매핑이면 그 안도 적힌 키만 재귀로 보며, 목록과 값은 같아야 합니다(`"warnings": []`는 경고가 없어야 한다는 뜻). 심볼릭 링크·깨진 YAML처럼 JSON 트리로 적기 어려운 사례는 `scripts/links.test.py`에 있습니다.
- **노트가 지정한 스크립트를 실행하지 않습니다.** 링크가 실행 파일을 가리켜도 해석만 하고, 해석에 쓰는 코드는 열람 도구 자신의 것입니다.
- **권한은 열람 도구가 검사합니다.** 해석 결과는 권한이 아닙니다.
- **태스크 앵커로의 이동**은 `dag.md`의 ID만의 heading을 대상으로 합니다. v2 장부의 `dag.md`처럼 ID heading이 없으면 문법은 받아들이되 이동할 곳이 없다고 표시합니다.
- 결과 여섯 가지와 `denied`를 사용자에게 구별해 보여 줍니다. "없음"과 "모호함"과 "범위 밖"을 하나로 합치지 않습니다.

## 6. 정하지 않은 것

- 장부 저장소가 여럿일 때의 등록부(어느 저장소가 "등록된 장부"인가)는 하네스 정의 저장소의 등록부가 정합니다(설계 §7.1). 지금 리졸버는 `--root` 하나를 받습니다.
- 커밋 고정 주소가 가리키는 파일·앵커가 그 커밋에 실제로 있는지는 확인하지 않습니다(네트워크·다른 저장소 접근 없음).
