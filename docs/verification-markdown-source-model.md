# Markdown verification source model

This is a headless data layer based on source 8aa04a02fde6c04e2f5177ab027fa1c49a7826de. It is a new implementation; it does not restore or claim identity with the unavailable 61cdafce candidate. No renderer component, bridge IPC contract, query pin, permission writer, Git reader, model adapter or installed package is changed.

`createTaskVerificationReader` consumes the existing task-evidence bridge. Every load requests bounded task-record discovery and fresh main-issued capabilities. The reader never opens a path or follows a Markdown link. Unused derived reference/image capabilities are released. Call `dispose()` when the consumer exits; a new load releases the previous session. The consumer must discard superseded results and refresh on source/permission changes; the returned claims are point-in-time observations, not durable permission grants.

`present` means eligible source prose was read. `none` means discovery was complete and all eligible Markdown bodies were read without a record. `unknown` means discovery, reading, task association or declaration parsing could not be completed. An unknown result may retain separately read claims, except session retirement/revocation/cancellation or a thrown bridge read failure withdraws all claims. Each record binds to its actual source hash, observation time and opaque evidence capability.

Exact `inbox/<taskId>/review-N.md` contract files are review records. Assignment, implementation and final contract files supply Verification sections. Explicit task-declared noncontract Markdown must contain exactly one matching task heading; only that subtree can supply Verification text. Other task contract paths, conflicting/nested task headings, duplicate declarations, empty declarations, invalid heading separators, unfinished fences and bounded Markdown parsing failures remain unknown. Common project documents and common links do not establish a task review. Additional arbitrary review filenames are deliberately not classified as reviews.

Multiple anchors of the same exact relative file are grouped before reading; there is at most one review record per file. A review file can separately contain a Verification record. Source prose is kept as source prose, with `assessment: not-assessed`, and reviewer identity, target SHA and independence remain unconfirmed even when the text declares PASS, done or bot approval.

The focused synthetic tests cover parsing/association, deduplication, incomplete discovery, capability refresh, late reads/preparation, revocation and derived-session cleanup. Integration tests use the existing evidence reader on isolated local files, covering changed source hashes, real reader authorization revocation and symlink replacement. Existing evidence and document-runtime tests are also run. No real model or company data is used.

UI layout, popover interaction/focus/accessibility and actual rendered UI review remain pending until the three Library reference images can be materialized and their pixels inspected. No claim of whole-app completion, full-suite validation or Electron UI validation is made for this data-only candidate.
