# Phase 2 논의 필요 — 검증·리뷰 중심의 오케스트레이션 보조

문서 ID: `P2-DISCUSSION-2026-10-07`. 기록일: **2026-10-07 KST**. 상태: **논의 필요（방향 합의 반영）**. 사용자의 제안과 이후 합의를 보존하는 기록이며 구현 착수나 작업 완료 선언이 아니다. Phase 1 실제 Mac 검증은 계속 진행한다.

## 이후 사용자 합의 — 실행은 Orca, note-app은 관측·리뷰·권고

사용자는 기존 에이전트 실행을 Orca로 충분히 하고 있으므로 note-app에 겹치는 실행 기능을 만들지 않기로 했다. **Phase 2는 관측·리뷰·파견 보류 권고**까지의 방향에 합의했다. 에이전트 실행과 파견은 Orca가 담당하며, note-app의 직접 개발 위임이나 강제 파견 제어는 새 범위에서 제외한다. 기존 계획은 아래 관계표에 이력으로 남긴다. 이 합의는 Phase 2 구현 착수 승인이 아니다.

프로젝트에 해당하는 Orca 앱/화면으로 포커스를 전환하는 연동은 **지원 여부 조사 후 가능한 경우에만 포함하는 선택 항목**이다. 불가능하면 건너뛰어도 된다는 사용자 조건을 보존한다. 프로젝트와 Orca 화면의 대응 식별, 제공 API/CLI, 실제 포커스 동작과 필요한 권한은 미확인이다.

부모 권고는 프로젝트 선택 시 note-app 상세를 유지하고 별도 **‘Orca에서 열기’ 버튼**을 두는 것이다. 이 세부 UI는 사용자 확정 요구와 구분하며 아직 권고다.

## 이후 사용자 순서 합의 — 화면을 먼저 검토

사용자가 요청한 진행 순서는 **가벼운 HTML 프로토타입 → 화면·렌더링·라이브러리 논의 → 합의한 화면에 맞춘 DAG 태스크 설계**다. 프로토타입은 별도 제작 중이며 이 기록 작업에서 중복 제작하거나 Phase 2 제품 구현에 착수하지 않는다. T-029~032는 화면 합의 후 재설계할 개념 계획으로 보존한다. 아래 초기 세 축과 권고는 이 순서의 입력이며 사전 확정 구현 태스크가 아니다.

후속 화면 합의: QA가 100건 이상을 검토하며 리뷰 부담을 느낀 사용자 경험을 바탕으로 여러 프로젝트를 오가는 흐름을 지원한다. 프로젝트 목록은 **항상 왼쪽**에 두고, 선택 프로젝트의 오른쪽은 요약·사용량·태스크 DAG를 한꺼번에 배치하지 않고 **2차 탭**으로 나눈다. **태스크 목록을 기본**으로 하고 선택 태스크는 오른쪽 미리보기로 보여준다. 사용자 경험의 프로젝트 사적 내용은 공개하지 않는다.

부모가 프로토타입에 반영하겠다고 답한 흐름은 프로젝트별 선택·탭·스크롤 유지다. HTML 변경은 별도 worker가 진행하며 이 기록에서 제품 Phase 2 구현을 시작하지 않는다. 각 탭의 상세 구성과 렌더링/라이브러리 검토는 화면 합의 과정에 남아 있다.

## 사용자 전제와 원문 해석

AI 시대의 병목은 생산성보다 검증·확인·리뷰다. 에이전트가 스스로 검증할 도구를 갖추고, 사람이 결과를 쉽게 리뷰할 수 있으며, 잘못된 코드의 유입을 구조적으로 제한하는 방향을 논의한다.

사용자 원문은 “올바르지 않은 코드는 구조적으로 삽입될 수 있도록 제한”이다. 문맥상 **잘못된 코드의 유입을 방지하거나 제한**한다는 뜻으로 해석했다. 원문 자체를 확정 요구로 고쳐 쓰지는 않으며, 구체적인 차단 지점과 예외 정책은 논의가 필요하다.

Phase 1은 Orca 오케스트레이팅을 보조하면서 기존 note를 읽는 기반이다. 아래 세 축은 Phase 2 추가 논의안이다. 새 구현·자동 파견·자동 DAG 쓰기를 승인한 것으로 해석하지 않는다.

## 1. 병렬 에이전트의 유한 자원 분배

사용자 제안은 우선순위에 따라 계정, Claude/Codex 사용 한도, 메모리를 분배하는 것이다. CodeBurn의 프로젝트별 금일/총 토큰 사용량과 필요한 경우 그래프, Orca CLI의 현재 실행 세션 확인을 활용한다. 관측 시점은 polling 또는 창 활성 시 확인을 고려한다. Electron에서 메모리 관측이 가능한지 확인하고 실제 점유·가상 메모리 등을 함께 검토하여 추가 파견 가능 여부를 판단한다.

사용자는 Codex가 이슈 네 건을 위해 Orca 워크트리를 병렬 생성하고 브리핑을 동시에 전송한 뒤 메모리가 급증해 Mac을 재부팅한 경험을 제시했다. 이는 사용자 경험 기록이며, 프로세스별 측정이나 원인 분석이 완료된 사실은 아니다.

`CLAUDE.md`/`AGENTS.md`의 구조적 실행 규칙과 note-app의 프로젝트별 메모리 표시를 함께 고려한다. 사용자는 Orca에도 워크트리별 메모리가 있는 것으로 알고 있으나 잘 확인하지 않게 되는 UX여서 note-app으로 가져오고 싶다고 설명했다. **Orca의 해당 capability와 단위·범위·freshness는 아직 확인하지 않았다.**

논의할 항목:

- 프로세스→세션→워크트리→프로젝트 귀속 방법과 공유 프로세스/종료된 세션의 처리
- RSS·공유 메모리·가상 메모리·압력·swap 중 표시할 지표와 이중 합산 방지
- 계정 한도, 사용량, 토큰 집계, 과금액, 실행 허가의 구분 및 unknown/stale 처리
- 우선순위, 동시 실행/대기/회복 정책과 실제 측정 후 정할 임계치
- 규칙의 권고와 강제 차단 지점, 사용자 override와 감사 기록
- 관측 비용을 줄이는 활성/배경 수집 주기와 추가 파견 전 확인 범위

기술 근거 확인(문서 대조, 제품 구현 검증과 구분): Electron은 자기 프로세스와 시스템 메모리 조회를 제공한다. macOS의 `getProcessMemoryInfo()`에는 `residentSet`이 없으며, `getSystemMemoryInfo()`의 `swapTotal`/`swapFree`는 macOS 항목이 아니다. 지표를 다른 OS에서 그대로 가져와 0으로 표시하지 않아야 한다. [Electron process 공식 문서](https://www.electronjs.org/docs/latest/api/process).

`app.getAppMetrics()`는 해당 Electron 앱 프로세스 범위다. 외부 에이전트·다른 앱·프로젝트 전체 메모리를 직접 제공한다고 해석할 수 없다. [Electron app 공식 문서](https://www.electronjs.org/docs/latest/api/app#appgetappmetrics). Apple은 메모리 압력에 여유 메모리, swap rate, wired memory, 파일 캐시 등을 고려한다고 설명한다. 여유 메모리 수치 하나로 추가 실행 허가를 결정하는 기준은 아직 없다. [Apple Activity Monitor 안내](https://support.apple.com/en-euro/guide/activity-monitor/-actmntr1004/mac).

외부 프로젝트별 메모리는 설치된 Orca의 실제 제공 항목과 프로세스 귀속을 조사해야 하며 **미확인**이다. 이 조사는 후속 논의 범위이며 Phase 1 구현 범위를 바꾸지 않는다.

## 2. 큰 DAG의 읽기와 필터

기존 설계는 note의 `*-dag-stack` 스킬로 `DAG.yaml`을 읽고 스크립트로 `DAG.md`를 만들어 Obsidian에서 보는 방식이다. 복잡해지면 그래프가 커지고 태스크 접두사가 다른 sub-DAG나 페이즈가 생긴다. 사용자 제안은 note-app에서 접두사/기능별 필터, 다이어그램 그래프와 태스크 필터를 제공하는 것이다.

논의할 항목:

- 원본 ID와 프로젝트별 컨벤션을 보존하는 접두사·기능·페이즈·상태 필터
- 필터 바깥 의존성, 숨겨진 노드 수와 막힌 경로를 표시하는 방식
- 그래프와 태스크 목록의 선택 동기화, 큰 DAG의 점진 렌더링/성능 측정
- 다중 sub-DAG 관계를 읽는 스키마와 누락·순환·미확인 표시
- 기존 YAML→Markdown/Obsidian 흐름과의 공존 및 원본 변경 없이 읽는 범위

부모 에이전트가 수행한 읽기 조사 결과(원문 프로젝트 내용은 공개하지 않음): 최근 표본 6개와 구형 표본 2개, 주 DAG 1,127태스크를 확인했지만 한 저장소 계열에 편중돼 전체 생태계 대표성을 보장하지 않는다. 소속은 `phases[].tasks[]`이며 접두사와 phase는 별개다. 관측 상태는 `pending/running/blocked/in_review/review_required/committed/done/deferred/superseded`였고 `PASS`/`skip`은 태스크 상태로 관측하지 않았다. 사용자 제안의 상태 예시와 실제 관측 목록을 구분한다.

여러 DAG 파일과 `retired_at/moved_to/migrated_tasks` 포인터, `external_depends_on` 및 불명 대상, `project_policy` 개정 리스트가 있었다. 계획의 done과 구현의 done은 같지 않다. MD/JSON/PNG/log로 근거가 분산되고 wikilink 형식도 다양했다. 단일 상태로 자동 정규화하거나 mtime만으로 완료를 추론하지 않아야 한다. JSON 내부의 최종 조회는 연결 끊김으로 미확인이므로 **근거 파일의 존재와 판정 진위는 별개**다. 이 내용은 부모가 전달한 구조 관측이며 이 Mac 검증 세션에서 타 프로젝트 원문을 추가 열람한 결과가 아니다.

후속 사용자 결정: 약 반년의 DAG 운영 경험을 바탕으로 **가장 최신 프로젝트들의 명시적 DAG 방침을 앞으로의 기본 운영 기준**으로 삼는다. 조사한 최신 note-app 및 세 프로젝트의 정책을 기본 기준으로, 구형 두 프로젝트 형식은 호환·마이그레이션 대상으로 구분한다. 불필요한 비공개 프로젝트명과 원문은 이 공개 기록에서 제외한다. 최신 프로젝트 사이에도 저장소별 완료 기준 등 의도적 차이가 있으므로 보존해야 한다. **파일 mtime 자체가 정책 우선권을 확정하지 않으며 명시 정책·개정 관계·적용 범위를 기준으로 해석**한다. 구형 상태를 무조건 최신 상태로 바꾸거나 기록의 의미를 지우는 합의가 아니다.

## 3. 태스크 단위 요약과 검수 근거

inbox는 상세 설계와 세션 맥락 복원·인계에 쓰이지만 사람이 매번 읽지는 않는다. 그 결과 태스크가 왜 생겼고 어떤 파일을 바꿨으며 무엇을 검증해 완료·미완료·PASS를 판단했는지 반복 질문하게 된다. 사용자 제안은 사람의 리뷰와 에이전트의 맥락 복원을 함께 지원하는 태스크 요약이다.

`pulls.review`의 교훈을 바탕으로 다음 항목을 고려한다. 여기서 교훈은 사용자 제안의 출발점이며 비공개 원문을 수집하거나 검증했다고 주장하지 않는다.

| 구성 | 논의할 내용 |
| --- | --- |
| 유형/상태 | 작업·계획, 백로그·진행·코드리뷰·검토·완료·스킵. 프로젝트별 DAG 컨벤션을 존중하고 무조건 공통 상태로 치환하지 않음 |
| 추가 이유 | 발생 배경, 해결할 문제와 목표, 관련 설계 |
| 수행 내용 | 변경 파일과 동작, 실제 수행 범위와 제외 범위 |
| 필요한 논의 | 미결정 사항, 사용자 판단이 필요한 tradeoff |
| 설계 연결 | 기존 wikilink와 앱 다이얼로그의 열람/경로/권한 경계 |
| 검증 근거 | 검증 범위·환경·명령·결과·시점, 스크린샷·오류 로그·E2E 경로 |
| 판정 | 완료·미완료·PASS의 근거와 미실행/실패/오래된 근거. DAG 선언·CI 성공·사용자 승인 구분 |

사용량과 메모리 낭비를 줄이기 위해 **별도 ‘태스크 요약’ 버튼을 눌러 생성**하는 방식을 제안했다. 자동 생성은 확정하지 않았다. 입력 선택·크기·민감정보 안내, source hash와 캐시/중복 방지, 변경 후 stale 표시, 취소·실패·근거 누락, 원문 링크와 요약의 구분을 논의해야 한다.

## 진행 순서와 남은 결정

사용자 합의의 우선 순서는 HTML 프로토타입과 화면 논의다. 이후 태스크 설계에 대한 에이전트 권고는 읽기 전용 자원 관측·귀속의 신뢰성을 확인하고 큰 DAG 필터·근거 링크를 나눈 뒤 수동 태스크 요약의 평가 기준/입력 계약을 정하는 것이다. 이 권고가 화면 합의 전 구현 순서를 확정하지 않는다. 자동 파견과 강제 차단은 현재 note-app 범위에서 제외한다.

부모의 이전 권고는 관측·리뷰·파견 권고를 먼저, 강제 제한은 후속으로 가져가는 방향이었다. 이후 사용자는 관측·리뷰·파견 보류 권고에 합의하면서 **실행은 Orca에 맡기는 범위**로 좁혔다. 이전 미결정 기록은 이 후속 합의로 갱신한다. 지표·필터·요약 계약, 첫 구현 범위, Orca 전환 지원 및 세부 UI, 완료 판정과 사용자 검수 방법은 여전히 논의가 필요하다. 현재 Phase 1의 미검증 항목을 Phase 2 계획으로 대체하지 않는다.
